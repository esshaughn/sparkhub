# Spark Hub

One app, many groups (Torrez Fitness is one, code TORREZ). Static HTML/CSS/JS (no build step), Supabase for data, deployed by Vercel on every push to `main`. See README.md for structure.

**Renamed 2026-09-25:** live address https://gosparkhub.vercel.app (since 2026-09-29 also https://sparkhub.wereallneighbors.org: an `A` record to Vercel in the domain's DNS at Hostinger (registered at Namecheap), listed in `LIVE_HOSTS` in `js/config.js` and `api/preview.js`) (the Vercel project is `gosparkhub`; the old torrezhub.vercel.app redirects), GitHub repo `esshaughn/sparkhub`, Supabase projects `sparkhub` / `sparkhub-test`, daily backups in `~/Backups/sparkhub` (launchd `com.sparkhub.backup`). The local folder was renamed from `sparks-torrez` to `sparkhub` on 2026-09-27.

## Design files

`design/spark-hub/` holds the current design spec (`README.md`, the decision log, and the clickable `Spark Hub App.dc.html` prototype; open it with `support.js` beside it). Photos, screenshots and explorations stay in the design zip. Where the README and `HANDOFF-to-design.md` disagree, the handoff records the owner's later decisions.

## Keep HANDOFF-to-design.md current

`HANDOFF-to-design.md` tells Claude Design how the live app differs from the last design file. Update it **in the same commit** as any change a user could see or do differently: layout, copy, screens, flows, states (empty/loading/error), what data is shown and to whom.

- New visible change → add a row to **§1 What changed** (change · what the design said · why).
- New UI the design never specified → add it to **§2 Things the build had to invent**, with the exact copy and key colors/sizes.
- Behaviour with no visual change (routing, permissions, sync) → **§3**.
- Something designed that's missing or broken → **§4**. A decision only Design can make → **§5 Open questions**.
- If a change undoes or supersedes an existing entry, edit or remove that entry. Don't stack contradictions.
- Bump the **As of** date.
- Skip it for pure refactors, performance, dependency bumps or infra changes with no user-facing effect.

When the user says a design round has absorbed the doc ("design synced", a new .dc.html handoff arrives, etc.), reset it: make the new design file the **Baseline**, clear §1–§4, and keep only the §5 questions that are still open.

## Database changes (migrations)

The schema is the files in `supabase/migrations/`, applied in order. Never edit an applied migration. Add a new one.

1. `supabase migration new <short_name>` and write the SQL (keep RLS: guests' names and any older phone numbers in `guest_contacts` must stay readable only by that idea's lead and the guest).
2. Apply to **test**: `scripts/db-push-test.sh` (refuses unless the folder is linked to test; allowed without a prompt) → try it on the `test` branch preview. Always `cat supabase/.temp/project-ref` before any other `--linked` command: on 2026-09-29 the folder was silently linked to live.
3. Apply to **live**, only when the matching code is being merged to `main` and the user has agreed: `scripts/db-push-live.sh` (links to live, pushes, lists migrations, and always relinks to test; pre-approved in the owner's auto-mode settings when they've asked in chat, 2026-09-30).
4. Check with `supabase migration list --linked [--project-ref …]`.

Ad-hoc reads: `supabase db query --linked [--project-ref …] "select …"`.

**Never run `supabase config push` against live** without showing the user the diff first. It pushes `supabase/config.toml`'s settings (auth, storage…) over the dashboard's. `enable_anonymous_sign_ins` must stay `true` or the app breaks.

## Keep-alive and backups

- `.github/workflows/keep-supabase-awake.yml` pings both projects daily so the free plan doesn't pause them. It only runs from `main`, and GitHub disables it after 60 days without commits.
- `scripts/backup-live.sh` dumps every live table to `~/Backups/sparkhub/<date>/` as JSON (keeps 30). It runs daily at 03:30 on the user's Mac via launchd (weekly until the Torrez pilot, 2026-09-30) (`scripts/install-backup.sh`; rerun the installer after editing the script). Backups contain names and phone numbers: **never commit or upload them.**
- The backup saves every public table that exists (it lists them first), so it keeps working as migrations add and drop tables.
- To restore: apply migrations to an empty project, recreate `auth.users` rows from `users.json` and their sign-in identities from `identities.json`, then insert the table files in order: groups, memberships, group_bans, profiles, sparks, offers, interests, guest_contacts, link_access, then the plan tables (spark_groups, rsvps, date_options, date_votes, spot_options, spot_votes, signup_items, signup_claims, plan_updates, organizers, plan_prep, album_photos, reactions), then event_drafts. (Backups from before 2026-09-25 have an older date_options/rsvps shape from the first build; don't restore those into the new tables.)

## Working in a cloud session (e.g. started from the Claude mobile app)

- `git push` is all a deploy needs. Vercel builds from GitHub, so no Vercel CLI or token is required.
- Database changes need the Supabase CLI plus a `SUPABASE_ACCESS_TOKEN` in the cloud environment's settings. Use `npx -y supabase@latest …` with the commands above. If the token isn't set, write the migration file and tell the user it still needs applying rather than skipping it.
- Preview locally with `npx -y serve .` if you need to click through the app. Localhost uses the test database.

## Tests

- `tests/` holds Playwright end-to-end tests (smoke, posting, groups, collaboration, Google sign-in, database security). The "End-to-end tests" workflow sizes each run (see the top of `.github/workflows/e2e.yml`): a push to `test` runs only the **quick suite** (`smoke` + `security`); the **full suite** runs nightly on `test` (only if `test` changed in the last 24 hours), on pull requests, and by hand. A **middle** run (the quick suite plus chosen spec files) is `gh workflow run e2e.yml --ref test -f suite=some -f specs="groups post"`. **What `main` needs (owner, 2026-10-01; three tiers):** a **small change** (screens, copy, layout, a new pop-up or button, with its local spec passing) goes live on a **green quick run** on that commit; don't wait for or start a full run. A **medium change** (how one feature loads, saves or syncs, notifications/push, or a change across several screens) needs a **green middle run** on that commit: the quick suite plus the specs for the areas touched (`gh workflow run e2e.yml --ref test -f suite=some -f specs="plans notifications"`). A **big change** (a migration, sign-in, accounts or merging, security rules (RLS, grants, storage policies), or app-wide data plumbing: `loadAll`, the start-up cache, `guardedFetch`) needs a **green full run** on that commit: the nightly one, or start one with `gh workflow run e2e.yml --ref test -f suite=full` and wait for it. When unsure between small and medium, run the specs for what you touched; when unsure whether it's big, it's big. The nightly full run on `test` is the backstop for what a middle run misses. Pushes that only touch `*.md`, `design/`, `scripts/`, `icons/`, `supabase/templates/`, `supabase/test-only/`, `.vercelignore` or the keep-awake workflow skip the run, so there's nothing to wait for.
- New features get a test in the same commit; removed features lose theirs. Security rules (RLS, grants, storage policies) get an assertion in `e2e/security.spec.js`.
- **Database checks without TEST:** `tests/db/run.sh` (Docker) starts a throwaway Supabase Postgres, applies `tests/db/stubs.sql` (what Auth/Storage create on a real project) and every migration, then `tests/db/checks.sql`, which signs in as made-up people and asserts what's allowed and refused. Nothing leaves the machine and it costs no Supabase quota, so run it after writing a migration, before `db-push-test.sh`; add a check there for each new rule too.
- The e2e leads are exempt from the rate limits (`private.rate_exempt`, added by `scripts/test-leads.py`); after rotating `E2E_LEAD_PASSWORD`, `python3 scripts/test-leads.py --reset-password` sets it on all six. CI never records Playwright traces (they hold request bodies, so the password) and deletes every zip before uploading a report.
- `supabase/test-only/nightly-cleanup.sql` also adds `e2e_update_recipients()` (who a host's update would reach, [E2E] events' leads only) and `e2e_forget_requests()` (clears friend requests between two e2e leads, since declined ones never go away). Re-apply it to TEST when it changes.
- Tests create ideas titled `[E2E] …` and delete them in `finally`. Each simulated member is a new anonymous sign-in. Posting needs a signed-in lead in a group, so `newLead(browser, 1|2)` signs in as a lead from Node and starts the browser with that session, already in Torrez Fitness (one page load; until 2026-10-02 it signed in inside the page, which cost three loads and an anonymous account per lead) (all Torrez Fitness members; group tests also create `[E2E] …` groups) (password accounts on the TEST project only; password in git-ignored `tests/.env` and the `E2E_LEAD_PASSWORD` repo secret). **CI runs 3 tests at a time** (since 2026-09-30; a full run went from ~7½ to ~3 minutes): each Playwright worker uses its own pair, worker 0 → `e2e-lead-1/2`, worker 1 → `3/4`, worker 2 → `5/6` (`leadEmail()` in helpers.js; `scripts/test-leads.py` creates them, TEST only). Locally it's one at a time unless `PW_WORKERS=3`. Tests that assume they're alone in Torrez Fitness (exact counts, empty states) must not be added; check your own `[E2E]` items. An account made in the last 20 minutes counts as new to the invite flow, so right after creating leads the groups test can fail once. The real email-code flow can't be automated (no inbox), so check it by hand on the preview after changing sign-in code.
- **Supabase free-plan quota.** Since 2026-09-29 live and test are in **separate** free organizations (`sparkhub-live`, `sparkhub-test`; the old `esshaughn` org is empty), so test traffic can't restrict live. Each has 1 GB log ingestion (not enforced until 2027) and 5 GB cached egress (photo downloads). In the week of 2026-09-21, when they still shared one, 159 CI runs plus local runs used 2.1 GB of logs and 6.4 GB of cached egress. Going over can still restrict the test project, so keep test traffic light:

  - Locally, run only the specs your change touches (`npx playwright test e2e/post.spec.js`), before pushing. Leave the full suite to the nightly run, or run it by hand once before a merge to `main`.
  - Push to `test` in batches (several commits per push), not after every small commit. Every push still runs the quick suite, and every full run by hand is the whole suite.

Anything that adds page loads to many tests adds load here.

## Security rules the code relies on

- Clients can only UPDATE these `sparks` columns: text, hopes, spot, spot_open, day, day_date, day_time, spot_address, spot_lat, spot_lon, vision, mood, cover_pos (column grants, `20260925000000_spark_hub_groups.sql`), plus visibility, auto_remind, min_people (`20260926000000_plans.sql`; `planned` was revoked in `20261101060000_planned_by_function.sql`: it changes only through `make_plan()` / `clear_plan()` or on insert), day_end (`20261008000000_post_flow.sql`) and guest_invites (`20261030000000_friends.sql`). Anything else goes through a `security definer` function. A new editable column needs a new grant in a migration.
- Groups: members see their groups' ideas; `open_idea()` records an idea link in `link_access`, which lets that visitor see that one idea. The app calls it only for an event the person can't already see (`openLink`). Since `20261101040000_group_access.sql`, `link_access.via` is `link` (open_idea) or `invite` (`invite_friends()`); `remove_member()` and `leave_group()` delete that person's `link` rows for the group's events (home or posted to it), invites stay. `remove_member(p_group, p_user, p_block default false)`: with `p_block` it also adds a `group_bans` row (no client access), and `join_group()` treats a blocked person like a wrong code (and skips `join_also` groups they're blocked from); admins list and lift blocks with `group_blocked()` / `unblock_member()`. Owners give a group a new code with `rotate_group_code()` (the old link and code stop working; `TORREZ` and `HUNTER` are fixed codes that scripts, tests and the pitch page use, so don't rotate those without updating them). `groups.code` isn't a readable column (only `group_code()` for admins). Admins of a group can delete any of its ideas (policy) and edit their text/basics only through `admin_edit_spark()`. Group photos and their framing change only through `set_group_photo()` (admins, and only to a photo in their own storage folder); idea covers through `set_idea_cover()` (lead) or the lead's `cover_pos` update. Owners rename/delete groups with `rename_group()` / `delete_group()`; `create_group()` and `rename_group()` refuse a demo group's or a roster group's name (`20261101050000_roster_by_id.sql`). Members may update only their own `last_seen_at` and `pinned`. Memberships are created only by `create_group()` / `join_group()`. Since `20261013000000_join_also.sql`, `join_group()` also adds a plain membership in every group listed for the joined one in `join_also` (no client access; set by hand in SQL): joining Torrez Fitness adds Hub on Hunters (only; the owner decided against Walnut Creek and Woodcliff, 2026-09-30), so a new member's Calendar isn't empty. Signed-in people may read `groups.demo` (`20261016000000_demo_groups.sql`; the app shows a DEMO chip after a demo group's name) but not change it. Joining, starting a group and posting require a signed-in (non-anonymous) account (`is_signed_in()`).
- Plans (V5, `20260926000000_plans.sql`): since `20261018000000_ideas_until_locked.sql` an event is an idea until the host locks it in: a plan needs a date (`sparks_plan_has_date`; the time and place may be to be decided), Create event posts undated events as ideas, `make_plan()` refuses without a date or while the idea is looking for a lead (`wants_host`, `20261101200000_plan_needs_lead.sql`) and pushes to the groups, `clear_plan()` takes the date off and notes everyone going, and `hopes` (Basic details) holds up to 3 lines of 60 (`20261101180000_details_60.sql`; was 40). An event can post to several groups: `group_id` is its home group (whose admins can delete it) and `spark_groups` rows add more; only the lead adds (groups they belong to, not the home one) or removes them, and members of any of them count for visibility. Drafts of the post flow live in `event_drafts` (one JSON row per draft, only its owner can read or write it, 20 max). The lead may update a sign-up's item, need, time, end_time and descr in place (Edit what you need). Who a host's update reaches is `private.update_recipients()` (`20261101000000_update_recipients.sql`): *hasn't replied* goes only to members of the event's groups who can see it (the same rule as `can_see_spark_row`: a whole-group event, or they lead it, run that group, or hold a link), roles read from `memberships` for each person, never `is_admin()` / `can_see_spark()` (those check the host). Who sees a spark is `can_see_spark_row()` (the sparks policy, which checks the row's own columns so an insert can return its row) / `can_see_spark(id)` (every child table): link holders, or members when it's `visibility = 'group'`, they lead it, run the group, or have replied. RSVPs only on planned sparks, only for yourself. The lead is Going to their own plan (`20261101160000_lead_going.sql`): an after-insert trigger on planned sparks and `make_plan()` add the lead's Going row, the lead can change it like anyone, and `clear_plan()` doesn't turn hosts into interests. Only the lead sets a sign-up's `need`, `time`, `end_time`, `descr` or `shift_of` (v6 Update 5, `20261007000000_signup_jobs.sql`: a shift is its own `signup_items` row pointing at its job on the same event), posts `plan_updates` and reads/writes `plan_prep`; a trigger refuses claims past `need` and silently skips claims on a job row that has shifts (people claim the shifts). Restore shift rows after their job rows. `make_plan()` / `clear_plan()` are lead-only (interest ↔ Going). Album photo paths follow the photo path rule. Temporary demo ideas and plans come from `scripts/demo/seed-events.py` (after `seed-demo.py`, which makes the demo people and groups); it is retired since 2026-10-01, when Walnut Creek and Woodcliff became ordinary groups (`scripts/demo/walnut-woodcliff-real.sql`) and no group is a demo group any more. The only demo content is Hub on Hunters' own set (`scripts/demo/seed-hub.py`, owner 2026-10-01: 17 demo events beside real ones, photos in `scripts/demo/hub/<key>-N.jpg`, no tester content). `my_group_sizes()` returns member counts only for the caller's own groups (Groups page). `notif_state` (read state, notification topics, email choice) is one row per person, readable and writable only by that person. **Demo world** (`20260930000000_demo_world.sql`): `sparks.demo` / `groups.demo` are hidden flags clients can't change; a trigger on `auth.users` (`demo_world_on_sign_in`) applies `demo_roster` roles to a confirmed, non-`@example.com` account (only upward, owner only while the group has fewer than two); since `20261011000000_demo_optin.sql` it no longer adds anyone else to the demo groups, and since 2026-10-01 the roster holds only the owner's rows (no testers: `scripts/demo/plain-testers.sql`). `wipe_demo()` is gone (`20261101140000_quiet_tests_no_wipe.sql`): demo content changes only through the seed scripts, group by group. Test events (`sparks.test`) never push: `private.push_send` skips any push whose link is a test event. Since `20261003000000_hardening_2.sql` the trigger acts only on confirmed emails (roster roles are keyed by email, so keep "Confirm email" on in both projects' Auth settings), a `before insert` trigger on `sparks` resets `demo` and `created_at` for anything but the service role, and guests can only keep their `guest_contacts` row on an idea they can see (and may delete it). The roster, flags and wiper are data in `scripts/demo/demo-world.sql` (re-run it after re-seeding). Since `20261101050000_roster_by_id.sql` `demo_roster` is keyed by `group_id`, and the demo scripts pick groups by who started them (the owner's account) or by code, never by name alone. It replaced the old `test-only/pending-invites.sql`.
- Notes (`20261009000000_event_notes.sql`, v6 Update 7): `notes` rows are written only by `delete_event()` (the lead or a home-group admin; tells everyone going), `remove_signup()` (the lead or whoever added the job; tells the people signed up to it or its shifts) — each person reads and deletes only their own. The app deletes events and removes jobs through these functions, not plain deletes. `set_home_group()` lets only the lead move an event's home to a group it's already posted to and they belong to; the old home becomes an extra group.
- Reactions (`20261004000000_reactions.sql`, v6 Update 2): one row per person, event and kind (`heart`, `praise`, `party`, `thanks`, `again`). Anyone who can see the event reads them (thank-yous are public); only signed-in accounts add their own, and only on planned events they can see; you can delete only your own. The app loads them tolerantly, so a database without the table still works (no reactions shown).
- Cancel or delete (`20261025000000_cancel_or_delete.sql`, `20261026000000_cancel_and_remove_account.sql`): `cancel_event(p_spark, p_reason)` (lead or home-group admin) sets `sparks.cancelled_at` / `cancel_reason` (no client grant) and notes going, maybe and helpers (an idea: interested); a cancelled event refuses new rsvps, claims and interest (`refuse_if_cancelled` triggers) and gets no reminders. `delete_event(p_spark, p_quiet default false, p_reason default null)`: quiet deletes tell no one; the one-argument call still notes everyone (the old behaviour). The lead may delete any album photo on their event. `remove_account(p_user)` (demo_admins only; not admins) makes the caller owner of any group the user was the only owner of (`20261028000000_remove_account_takes_groups.sql`; returns those groups' names), deletes the user's led events and then the auth user (everything else cascades).
- Event types (`20261027000000_event_tags.sql`): `sparks.tags` (up to 2 of active / outdoors / food / family / social, checked by `sparks_tags_ok`), updatable by the lead (column grant). Existing rows got a one-time guess from their titles; `scripts/demo/seed-events.py` doesn't set tags, so re-seeded demo events come back untagged unless it's updated.
- Friends (`20261030000000_friends.sql`, v6 Update 13): `friendships` (one row per pair, `user_a < user_b`), `friend_requests` (a declined one stays, with `declined_at`, so the sender can't ask again), `friend_codes` (one 6-character friend-link code each) and `event_invites` have no client writes; the first three aren't readable at all. Clients read through `friend_state()` (friends with shared group names, incoming requests, sent requests, invites you've had) and write through `send_friend_request()` (needs a shared group; 30 an hour; makes you friends if they'd asked you), `answer_friend_request()`, `remove_friend()` (quiet; deletes the friendship and only your own pending request: declined requests stay, so the person turned down can't ask again, `20261101070000_friend_requests_keep.sql`), `my_friend_code(p_new)`, `add_friend_by_code()` (friends straight away; `self` / `bad` / `already`) and `friend_link_preview()` (anon too: name, photo, `is_you`; `20261030010000_friend_link_self.sql`). `invite_friends(spark, people[])` lets the lead, a home-group admin, or anyone going when `sparks.guest_invites` is on invite friends and, since `20261101170000_invite_people.sql`, members of the event's groups they share (`private.can_invite()`, `private.invitable()`; `event_invited(spark)` tells whoever can invite who already has an invite): it adds `event_invites` + `link_access` (so they can see and RSVP), skips people already going or invited, and pushes topic `friends`. The profiles policy also lets friends see each other (`is_friend()`). `group_people()` gives any member a group's names, photos, roles and join dates (no emails; admins still use `group_members()`).
- Notification audit (`20261023000000_notification_audit.sql`): `push_host()` skips an rsvp row written by someone other than that person (make_plan) and a Going within 2 minutes of that person's sign-up on the event; it also handles `interests` (trigger `push_host_interest`, skipping rows clear_plan moves). `push_new_event()` announces ideas too. `push_daily()` sends day-before and morning-of reminders to going, maybe and helpers (tags `r:{id}:{date}:1/0`).
- New-account alert (`20261020000000_new_account_push.sql`): a trigger on `auth.users` (`notify_new_account`) pushes to `demo_admins` the first time a person has a confirmed, non-anonymous email; `@example.com` never notifies; failures never block sign-up.
- New accounts list (`20261022000000_accounts_list.sql`): `new_accounts()` returns every account (same definition as the alert) with email, sign-in method and groups, only to `demo_admins`; everyone else gets no rows.
- View as a tester (`20261006000000_demo_view_as.sql`; since `20261101190000_view_as_anyone.sql` anyone sharing one of the caller's groups, demo people included): `demo_testers()` returns rows only to `demo_admins` — those accounts, and their memberships in the caller's groups. The app then redraws itself as that person without changing sessions, and `guardedFetch` (sparks.js) refuses every non-GET request except `POST /auth/v1/token` and `/auth/v1/logout` (the owner's own session) and the read-only RPCs in `READ_RPCS` while it's on; `saveName`, `savePe` and `googleSignIn` also stop early. Keep new read-only RPCs the preview needs in that list.
- Profiles (`profiles`): name, avatar_path, and since v5.2 `place` (≤40) and `bio` (≤160); writes allow only your own row. Reads (`20261003010000_profiles_private.sql`): your own, people you share a group with (through `shares_group()`, since the memberships policy hides other people's rows; fixed in `20261005000000_profiles_share_group.sql`), and people taking part in an idea you can see (lead, interested, replies, RSVPs, organizers, sign-ups, and since `20261004010000_reactions_profiles.sql` reactions). `memberSince` in the app is the auth user's `created_at` year.
- Roles are owner / admin / member (owners count as admins everywhere via `is_admin()`). In the app, owners change roles with `set_member_role()` (max five owners since `20261014000000_manage_members.sql`, never zero, enforced by a trigger and the function). `group_members()` (admins of that group only) returns each member's email and join date for the Members sheet; `remove_member()` lets admins remove members and owners remove anyone but themselves. `leave_group()` (`20261017000000_leave_group.sql`) lets anyone leave a group they're in, except its last owner. By hand, admins are per database: set with `update public.memberships set role = 'admin' where user_id = (select id from auth.users where email = '…') and group_id = (select id from public.groups where code = 'TORREZ')`. On test, esshaughn@gmail.com runs Torrez Fitness.
- Rate limits (`20261101020000_rate_limits.sql`): `private.rate_ok(user, kind, max, window, scope)` counts in `private.rate_hits`; before-insert triggers refuse with SQLSTATE `PT429` (HTTP 429; the app's `failed()` shows *You're going a bit fast…*): sparks 10/h per person, date_options and spot_options 10/h per person per event, interests 20/h, plan_updates 10/h per event, spark_groups 20/h. Only rows people write for themselves count (not clear_plan's moves, seeding or the service role). `private.rate_exempt` skips the e2e leads on TEST (added by `scripts/test-leads.py`); never add anyone on live. Host notifications for suggestions use one tag per event, and anything a guest does one `g:{event}` tag, so they replace each other on the host's phone.
- No passwords (`20261101100000_no_passwords.sql`): a trigger on `auth.users` blanks `encrypted_password` on every insert and update, except for `e2e-lead-1…6@example.com` (TEST only). Auth still accepts a password at sign-up, and on 2026-10-01 (DB-10) one set by whoever registered an address first still worked after the real owner confirmed it.
- Hosts and who came (`20261101090000_hosts_and_who_came.sql`, social-science review 2026-10-01): `sparks.wants_host` (no client grant) changes only through `set_wants_host()` (the lead of an unplanned, uncancelled idea); `step_back()` (`20261101210000_step_back.sql`, the lead only) hands the lead to the earliest co-lead, or turns a plan back into an idea that's looking for a lead (going → interested, notes, date and place kept); `take_the_lead()` lets any signed-in person who can see such an idea become its lead (lead_name from their profile, wants_host off), keeps the floater interested and notes them. `interests.can_help` is the only interest column clients update (own row). `rsvps.attended` (null = not checked) is set only by `mark_attended()` (lead or home-group admin, planned events from their day on, America/Chicago). **Supabase's default privileges give `authenticated` every column on new tables**: `20261101110000_rsvp_interest_column_grants.sql` revoked table-wide UPDATE on rsvps and interests (you could check yourself in, or move a reply onto an invite-only event to see it), the insert grant on rsvps is spark_id, user_id, status, and since the app upserts replies (which sets spark_id and user_id too) `20261101120000_rsvp_upsert_guard.sql` gives those back for update with a trigger, `rsvp_guard`, that refuses moving a reply or changing attended outside `mark_attended()`. A new table or column needs an explicit revoke, not just a narrower grant.
- Co-hosts (`20261101130000_cohosts.sql`): `cohosts` (spark_id, user_id, added_by) has no client writes; `add_cohost()` (a host or home-group admin; an account in one of the event's groups; 5 max; notes them) and `remove_cohost()` (the lead or an admin, or yourself). `is_host(spark)` = the lead or a co-host and replaces the lead check in the sparks update policy (mood photos may be in any host's folder, `host_photo_re()`), sign-ups, updates, prep, album removal, date/spot removal, guest contacts, spark_groups and in make_plan, clear_plan, add_offer, resolve_offer, remove_signup, set_home_group, set_idea_cover, invite_friends, mark_attended. Delete/cancel and set_wants_host stay with the lead (and admins). `private.host_ids()` gives push_host every host, and push_new_event/made_plan/daily and update_recipients treat co-hosts like the lead. In the app `isLead()` means any host and `isTheLead()` only the lead.
- Photo uploads (`20261101010000_photo_limits.sql`): `photo_upload_ok()` in the storage insert policy allows 50 photos in any 24 hours to a signed-in account and none to a guest (`20261101080000_guests_rsvp_only.sql`); the bucket's limit is 2 MB (the app uploads ≤1200px JPEGs, ~150–400 KB).
- Photo paths (idea photos, mood photos, avatars) must be `<uploader uid>/<uuid>.jpg`; the DB checks the shape and the insert policy checks the uid. `PHOTO_PATH` in sparks.js mirrors it. Don't build image URLs from unvalidated strings.
- `vercel.json` sets the Content-Security-Policy. Adding any new external script, style, font, image or API host means adding it there first, or production breaks silently (check the browser console for "Refused to…").
- `index.html` pins supabase-js with an `integrity` hash. When bumping the version, recompute: `curl -s <new url> | openssl dgst -sha384 -binary | openssl base64 -A`.
- All user text is rendered through `esc()`. Never concatenate raw strings into HTML or `style` attributes. `bg()` draws only our own photo addresses (storage URLs from `photoUrl()`, `/photos/…`, `blob:` / `data:image` for a just-picked photo) at a plain position; anything else is left out. Text helpers escape what they're given (`head6`, `secHead6`, `note6`, `inviteCard`, `sheetHead`, `heldNote`, the Edit sheet's `label`, Create event's `head`); `h3Html` / `paraHtml` take markup, so `esc()` any user text going into them.

## Other notes

- People sign in with Google or a 6-digit email code (Supabase email OTP). New email: `updateUser({ email })` + `verifyOtp({ type: 'email_change' })` links it to the anonymous session (same user id). Existing email: `signInWithOtp` + `verifyOtp({ type: 'email' })`, then `complete_merge` moves the anonymous session's activity across. Guests (not signed in, owner 2026-10-01) can only see the event whose link they were sent and RSVP with a first name (a `guest_contacts` row, no phone; `needGuest` in sparks.js); everything else goes through `needAccount`, which opens sign-in (*Create a free account*), and after a guest's Going or Maybe the app offers an account (*You're on the list*). The host is still notified of a guest's RSVP. The database enforces it (`20261101080000_guests_rsvp_only.sql`): restrictive *signed in only* insert policies on interests, date/spot options and votes, signup items and claims, album photos and organizers; a guest's RSVP needs their `guest_contacts` row; profile photos and uploads need an account; `add_offer()` too.
- "Continue with Google" (`googleSignIn` in `js/config.js`, per database): always `signInWithOAuth` + `complete_merge` (the merge token moves the guest's RSVPs, guest names and event links), one trip to Google. Until 2026-10-01 anonymous users tried `linkIdentity` first, which came back `identity_already_exists` for every returning account and sent them to Google twice; the second trip sometimes didn't finish (owner: one trip for everyone). "Allow manual linking" is no longer needed. The page reloads on return, so the draft (photos as data URLs), merge token and name are parked in sessionStorage (`spark-hub-google-resume`), with where sign-in started (post / join / group / profile) so the app picks up there. The client uses `flowType: 'pkce'` so the return lands in `?code=` and not in our `#/` routes. Each Supabase project needs: the Google provider (client ID + secret) and the site in Auth → URL Configuration. Names: the app's name is `user_metadata.display_name` (Google overwrites `name` with the full name on every sign-in).
