## Keep HANDOFF-to-DESIGN.md current

`HANDOFF-to-DESIGN.md` tells Claude Design how the live app differs from the last design file. Update it **in the same commit** as any change a user could see or do differently: layout, copy, screens, flows, states (empty/loading/error), what data is shown and to whom.

- New visible change → add a row to **§1 What changed** (change · what the design said · why).
- New UI the design never specified → add it to **§2 Things the build had to invent**, with the exact copy and key colors/sizes.
- Behaviour with no visual change (routing, permissions, sync) → **§3**.
- Something designed that's missing or broken → **§4**. A decision only Design can make → **§5 Open questions**.
- If a change undoes or supersedes an existing entry, edit or remove that entry. Don't stack contradictions.
- Bump the **As of** date.
- Skip it for pure refactors, performance, dependency bumps or infra changes with no user-facing effect.

When a design round has absorbed the doc (Design's `HANDOFF-to-CODE.md` says it caught up with ours, or the user says "design synced"), reset it: make that round the **Baseline**, clear §1–§4 of what Design took in, and keep only the §5 questions that are still open. **Never clear *Owner calls that stand***: a reset dropped the owner's calls before, so Design kept drawing the old versions and nobody noticed the clash.

## Database changes (migrations)

The schema is the files in `supabase/migrations/`, applied in order. Never edit an applied migration. Add a new one.

1. `supabase migration new <short_name>` and write the SQL (keep RLS: guests' names and any older phone numbers in `guest_contacts` must stay readable only by that idea's lead and the guest).
2. Apply to **test**: `scripts/db-push-test.sh` (refuses unless the folder is linked to test; allowed without a prompt) → try it on the `test` branch preview. Always `cat supabase/.temp/project-ref` before any other `--linked` command: on 2026-09-29 the folder was silently linked to live.
3. Apply to **live**, only when the matching code is being merged to `main` and the user has agreed: `scripts/db-push-live.sh` (links to live, pushes, lists migrations, and always relinks to test; pre-approved in the owner's auto-mode settings when they've asked in chat, 2026-09-30).
4. Check with `supabase migration list --linked [--project-ref …]`.

Ad-hoc reads: `supabase db query --linked [--project-ref …] "select …"`.

**Never run `supabase config push` against live** without showing the user the diff first. It pushes `supabase/config.toml`'s settings (auth, storage…) over the dashboard's. `enable_anonymous_sign_ins` must stay `true` or the app breaks.

## Tests

- `tests/` holds Playwright end-to-end tests (smoke, posting, groups, collaboration, Google sign-in, database security). The "End-to-end tests" workflow sizes each run (see the top of `.github/workflows/e2e.yml`): **a push to `test` runs nothing** (owner, 2026-10-03): when a batch is ready, start the **quick suite** (`smoke` + `security`) by hand with `gh workflow run e2e.yml --ref test -f suite=quick`; the **full suite** runs nightly on `test` (only if `test` changed in the last 24 hours), on pull requests, and by hand. **CI tests against its own throwaway Supabase by default** (`tests/local/start.sh` on the runner), so runs cost the TEST project nothing; add `-f db=test` to run against TEST. A **middle** run (the quick suite plus chosen spec files) is `gh workflow run e2e.yml --ref test -f suite=some -f specs="groups post"`. **What `main` needs (owner, 2026-10-01; three tiers):** a **small change** (screens, copy, layout, a new pop-up or button, with its local spec passing) goes live on a **green quick run** on that commit; don't wait for or start a full run. A **medium change** (how one feature loads, saves or syncs, notifications/push, or a change across several screens) needs a **green middle run** on that commit: the quick suite plus the specs for the areas touched (`gh workflow run e2e.yml --ref test -f suite=some -f specs="plans notifications"`). A **big change** (a migration, sign-in, accounts or merging, security rules (RLS, grants, storage policies), or app-wide data plumbing: `loadAll`, the start-up cache, `guardedFetch`) needs a **green full run on TEST** on that commit: start one with `gh workflow run e2e.yml --ref test -f suite=full -f db=test` and wait for it (a local full run first is free, so catch what you can there). When unsure between small and medium, run the specs for what you touched; when unsure whether it's big, it's big. The nightly full run on `test` is the backstop for what a middle run misses.

## Security rules the code relies on

- Clients can only UPDATE these `sparks` columns: text, hopes, spot, spot_open, day, day_date, day_time, spot_address, spot_lat, spot_lon, vision, mood, cover_pos (column grants, `20260925000000_spark_hub_groups.sql`), plus visibility, auto_remind, min_people (`20260926000000_plans.sql`; `planned` was revoked in `20261101060000_planned_by_function.sql`: it changes only through `make_plan()` / `clear_plan()` or on insert), day_end (`20261008000000_post_flow.sql`) and guest_invites (`20261030000000_friends.sql`). Anything else goes through a `security definer` function. A new editable column needs a new grant in a migration.
- Groups: members see their groups' ideas; `open_idea()` records an idea link in `link_access`, which lets that visitor see that one idea. The app calls it only for an event the person can't already see (`openLink`). Since `20261101040000_group_access.sql`, `link_access.via` is `link` (open_idea) or `invite` (`invite_friends()`); `remove_member()` and `leave_group()` delete that person's `link` rows for the group's events (home or posted to it), invites stay. `remove_member(p_group, p_user, p_block default false)`: with `p_block` it also adds a `group_bans` row (no client access), and `join_group()` treats a blocked person like a wrong code (and skips `join_also` groups they're blocked from); admins list and lift blocks with `group_blocked()` / `unblock_member()`. Owners give a group a new code with `rotate_group_code()` (the old link and code stop working; `TORREZ` and `HUNTER` are fixed codes that scripts, tests and the pitch page use, so don't rotate those without updating them). `groups.code` isn't a readable column (only `group_code()` for admins). Admins of a group can delete any of its ideas (policy) and edit their text/basics only through `admin_edit_spark()`. Group photos and their framing change only through `set_group_photo()` (admins, and only to a photo in their own storage folder); idea covers through `set_idea_cover()` (lead) or the lead's `cover_pos` update. Owners rename/delete groups with `rename_group()` / `delete_group()`; `create_group()` and `rename_group()` refuse a demo group's or a roster group's name (`20261101050000_roster_by_id.sql`). Members may update only their own `last_seen_at` and `pinned`. Memberships are created only by `create_group()` / `join_group()`. Since `20261013000000_join_also.sql`, `join_group()` also adds a plain membership in every group listed for the joined one in `join_also` (no client access; set by hand in SQL): joining Torrez Fitness added Hub on Hunters until 2026-10-03, when the owner said its link joins Torrez only (`20261103010000_torrez_joins_only_torrez.sql`); no group has a `join_also` row now. Signed-in people may read `groups.demo` (`20261016000000_demo_groups.sql`; the app shows a DEMO chip after a demo group's name) but not change it. Joining, starting a group and posting require a signed-in (non-anonymous) account (`is_signed_in()`).
- Plans (V5, `20260926000000_plans.sql`): since `20261018000000_ideas_until_locked.sql` an event is an idea until the host locks it in: a plan needs a date (`sparks_plan_has_date`; the time and place may be to be decided), Create event posts undated events as ideas, `make_plan()` refuses without a date or while the idea is looking for a lead (`wants_host`, `20261101200000_plan_needs_lead.sql`) and pushes to the groups, `clear_plan()` takes the date off and notes everyone going, and `hopes` (Basic details) holds up to 3 lines of 60 (`20261101180000_details_60.sql`; was 40). An event can post to several groups: `group_id` is its home group (whose admins can delete it) and `spark_groups` rows add more; only the lead adds (groups they belong to, not the home one) or removes them, and members of any of them count for visibility. Drafts of the post flow live in `event_drafts` (one JSON row per draft, only its owner can read or write it, 20 max). The lead may update a sign-up's item, need, time, end_time and descr in place (Edit what you need). Who a host's update reaches is `private.update_recipients()` (`20261101000000_update_recipients.sql`; since `20261104000000_event_updates.sql` also `coming` = going or maybe, and the push body is *First name: update*): *hasn't replied* goes only to members of the event's groups who can see it (the same rule as `can_see_spark_row`: a whole-group event, or they lead it, run that group, or hold a link), roles read from `memberships` for each person, never `is_admin()` / `can_see_spark()` (those check the host). Who sees a spark is `can_see_spark_row()` (the sparks policy, which checks the row's own columns so an insert can return its row) / `can_see_spark(id)` (every child table): link holders, or members when it's `visibility = 'group'`, they lead it, run the group, or have replied. RSVPs only on planned sparks, only for yourself. The lead is Going to their own plan (`20261101160000_lead_going.sql`): an after-insert trigger on planned sparks and `make_plan()` add the lead's Going row, the lead can change it like anyone, and `clear_plan()` doesn't turn hosts into interests. Only the lead sets a sign-up's `need`, `time`, `end_time`, `descr` or `shift_of` (v6 Update 5, `20261007000000_signup_jobs.sql`: a shift is its own `signup_items` row pointing at its job on the same event), posts `plan_updates` and reads/writes `plan_prep`; a trigger refuses claims past `need` and silently skips claims on a job row that has shifts (people claim the shifts). Restore shift rows after their job rows. `make_plan()` / `clear_plan()` are lead-only (interest ↔ Going). Album photo paths follow the photo path rule. Temporary demo ideas and plans come from `scripts/demo/seed-events.py` (after `seed-demo.py`, which makes the demo people and groups); it is retired since 2026-10-01, when Walnut Creek and Woodcliff became ordinary groups (`scripts/demo/walnut-woodcliff-real.sql`) and no group is a demo group any more. There is **no demo content** since 2026-10-03: the owner had every demo event deleted, on live (16, all Hub on Hunters) and TEST (17); backup `~/Backups/sparkhub/2026-10-03_1042`.
